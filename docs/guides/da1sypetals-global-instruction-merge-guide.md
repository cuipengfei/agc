# Da1sypetals 用户级规则合并指南

> Source rules: [`../references/da1sypetals-agents-md-reorg.md`](../references/da1sypetals-agents-md-reorg.md)
>
> Upstream: https://github.com/Da1sypetals/AGENTS.md/blob/main/AGENTS.md

## 用途

本指南说明如何把 Da1sypetals 规则合并进另一台机器已有的用户级或全局 agent 指令文件。

目标机器的宿主、文件路径、现有内容、自动加载方式和 symlink 关系都可能不同。本指南提供调查、合并和验证方法，不提供只能用于某一台机器的固定 patch。

## 核心原则

- 尽可能逐字保留 Da1sypetals 原文。这是最高合并原则。
- 先完整读取目标文件，再决定每条规则的位置。
- 相同含义只保留一个权威版本。
- 目标文件中的独有规则继续保留。
- 真正互相排斥的规则必须明确选择，不能混合成含义不清的新规则。
- 每条 source rule 都要登记为：原样合并、修改后合并或未合并。
- 文件名称、宿主机制和用户明确决定可以成为修改原文的理由。
- 语气、篇幅、工作量和个人写作习惯不能成为改写原文的理由。
- 多个宿主共用规则时，优先建立一个 canonical file；是否使用 symlink 取决于目标机器的真实加载机制。
- 不读取或记录凭据、token、cookie、会话历史和运行时状态。

## 术语

- **source rules**：Da1sypetals 重组文件中的规则。
- **target instruction file**：目标机器实际加载的用户级或全局指令文件。
- **canonical file**：多个宿主共享规则时采用的唯一来源。
- **host-specific rules**：只适用于某个宿主的规则。
- **原样合并**：规则正文逐字保留。
- **修改后合并**：因文件名称、宿主机制、现有规则冲突或用户决定而修改。
- **未合并**：经过明确判断后排除，并记录原因。

## 调查目标机器

修改文件前，建立宿主清单：

| 宿主 | 候选指令文件 | 路径类型 | symlink 目标 | 是否实际加载 | 是否含宿主专用内容 |
|---|---|---|---|---|---|
| `<host>` | `<path>` | 普通文件 / symlink / 不存在 | `<resolved-path>` | 已验证 / 未验证 | 是 / 否 / 未知 |

需要查明：

- 安装了哪些 agent 宿主。
- 每个宿主实际读取哪些用户级或全局指令文件。
- 哪些路径是普通文件，哪些路径是 symlink。
- 每个 symlink 的最终目标。
- 哪些宿主会自动加载另一个宿主的指令文件。
- 各个文件是否包含宿主专用规则。
- 各个文件之间是否已经出现内容分叉。
- 用户是否授权放弃任何分叉内容。
- 哪个文件适合作为 canonical file。

使用文件内容、`stat`、`readlink -f`、宿主官方文档或可观察行为确认这些事实。没有经过验证的加载关系必须标为“未验证”。

目标机器可能采用以下任一种结构：

- 只有一个用户级指令文件。
- 每个宿主维护独立文件。
- 多个宿主通过 symlink 读取同一个文件。
- 某个宿主自动加载另一个宿主的指令文件。
- 共享规则位于 canonical file，宿主专用规则位于其他文件。

## 修改前记录

记录以下信息：

- source rules 文件的 SHA-256。
- 每个目标文件的路径、类型和 SHA-256。
- 每个 symlink 的原始目标。
- Git staged、unstaged 和 untracked 状态。
- 当前宿主加载关系。
- 用户已经批准的保留项、修改项和排除项。

目标文件包含无法判断是否保留的独有规则时，停止修改并把这些规则交给用户决定。未经授权不得删除分叉内容。

目标文件已经 staged 时，另外记录 staged blob hash。后续验证必须证明原有 staged 内容没有意外改变。

## 建立 source rules 清单

逐条读取 source rules。列表项下面的示例、引用和嵌套列表属于该规则的一部分，不能只统计顶层列表项。

使用以下记录格式：

| 来源位置 | 完整原文 | 现有相关规则 | 处理状态 | 目标章节 | 原因 |
|---|---|---|---|---|---|
| `<line>` | `<source text>` | `<existing text or none>` | 原样合并 / 修改后合并 / 未合并 | `<heading>` | `<reason>` |

任何修改开始前，每条规则都必须获得处理状态。

## 判断规则关系

### 相同含义

保留一个权威版本：

- Da1sypetals 文字更明确时，采用其原文。
- 目标文件文字包含额外有效要求时，把独有要求保留下来。
- 删除被替换的旧句，避免同一规则出现两次。

### 相近但互补

两条规则分别控制不同环节时可以同时保留。例如：

- 一条要求依据证据陈述事实。
- 另一条要求回答“有没有”时避免假阳性。

这两条可以放在同一章节，各自保留。

### 真正冲突

两条规则无法同时执行时：

- 写出双方完整原文。
- 说明冲突发生在哪个行为上。
- 检查用户是否已经给出明确选择。
- 用户没有选择时，修改前暂停并请求决定。
- 用户选定后，只保留获准版本，并在审计表中记录。

工作量不能作为排除规则的理由。

## 合并规则

### 全局规则直接写入 canonical file

每次任务都会用到的内容应直接放进 canonical file，例如：

- 总则。
- 事实性陈述。
- 自我纠正和最终输出。
- 语言与句式。
- 回答态度。
- 用词。
- 默认禁止。
- 通用工作流程。

这些规则不能只放在需要 agent 再次读取的 context pointer 后面。

### 条件规则放入现有相关章节

代码实现、代码风格、测试和工具规则应进入目标文件已有的相关章节。目标文件没有对应章节时再新增章节。

不要为了复刻本指南或某台机器而创建重复标题。

### 保持原文

默认使用原文。修改仅限：

- 把 `AGENTS.md` 等固定名称改成目标机器真正使用的文件名称。
- 适配已经验证的宿主加载机制。
- 合并重复含义。
- 处理用户已经裁定的冲突。
- 执行用户明确批准的排除决定。

所有修改必须进入最终审计表，展示原文、最终文字和原因。

### 检查规则自身影响

source rules 可能新增用词和格式限制。合并后检查 target instruction file 的其他自然语言：

- 规则定义可以引用自己禁止的词语。
- 代码、命令、路径、identifier、skill 名称和不能修改的正式名称保持原样。
- 其他自然语言应符合新加入的规则。
- 不能以统一风格为理由改写 source rules。

## 选择共享方式

### 可以使用 symlink 的条件

满足以下条件时，可以让多个宿主通过 symlink 共用 canonical file：

- 多个宿主能够读取相同文件格式。
- 各宿主已经验证会加载相应路径。
- 用户希望这些宿主共享同一套规则。
- 被替换文件中的独有内容已经处理。
- 用户明确授权放弃或迁移分叉内容。

执行前记录普通文件内容和 symlink 状态。删除普通文件和创建 symlink 都需要用户明确授权。

验证命令可以包括：

```bash
stat -c '%F %N' <instruction-path>
readlink -f <instruction-path>
sha256sum <canonical-file> <instruction-path>
```

### 需要独立文件的情况

以下情况保留独立文件：

- 宿主要求不同格式。
- 宿主需要无法放进共享文件的专用规则。
- 宿主不会加载 symlink 指向的文件。
- 用户没有授权丢弃分叉内容。

独立文件继续维护共享规则清单，并把宿主专用规则放在明确标记的章节中。

### 自动加载

宿主已经自动加载 canonical file 时，不再创建内容副本。先用官方文档或可观察行为验证自动加载机制。

## 修改顺序

- 完整读取 source rules 和所有 target instruction files。
- 记录 hash、路径类型、symlink 目标和 Git 状态。
- 建立逐条规则清单。
- 处理重复内容和真正冲突。
- 修改 canonical file。
- 按用户授权处理独立文件或 symlink。
- 运行逐条规则审计。
- 验证每个宿主实际读取的内容。
- 核对 Git index 和 source rules hash。
- 验证全部通过后再报告完成。

## 修改后审计

使用以下表格：

| 来源位置 | 原规则 | 状态 | 最终位置 | 最终文字 | 原因 |
|---|---|---|---|---|---|
| `<line>` | `<full source text>` | 原样合并 / 修改后合并 / 未合并 | `<file:line>` | `<full final text>` | `<reason>` |

审计要求：

- 每条 source rule 都有一行。
- 原样合并的文字可以在目标文件中逐字匹配。
- 修改后合并展示修改前后的完整文字。
- 未合并规则写明用户决定或明确冲突。
- 分别统计三种状态的数量。
- 数量与逐条记录一致。
- 示例、引用和嵌套列表也经过检查。
- 没有未登记的遗漏。

## 确定性验证

至少检查：

- source rules 文件修改前后的 SHA-256 相同。
- 每条原样合并规则只出现一次。
- 每条修改后合并规则与审计表一致。
- 每条未合并规则没有意外进入目标文件。
- 被替换的旧规则已经移除。
- target instruction file 没有无意生成的重复规则。
- symlink 存在并指向预期文件。
- 多个宿主入口读取到的 canonical file hash 相同。
- 自动加载关系仍然有效。
- 修改前已经 staged 的内容没有改变。
- 没有修改未获授权的宿主配置。

发现失败项后继续修正并重新检查。存在失败项时不能报告全部完成。

## 人工恢复

修改前的记录必须足以恢复：

- 使用文件编辑工具恢复原 target instruction file 内容。
- 根据记录恢复普通文件或 symlink 类型。
- 使用 `rm` 和 `ln -s` 恢复原 symlink 关系。
- 恢复后重新检查路径类型、hash 和宿主加载结果。
- 不使用 Git 回滚用户级配置文件。

目标文件不受版本控制时，可以在用户授权后保存一份明确命名的备份。备份位置必须由用户确认。

## 当前机器示例

本节只记录本次已经验证的实例，不能当成其他机器的默认结构。

### 文件关系

- canonical file：`~/.claude/CLAUDE.md`
- Codex：`~/.codex/AGENTS.md` symlink 到 canonical file
- OMP：`~/.omp/agent/AGENTS.md` symlink 到 canonical file
- OpenCode：自动加载 canonical file
- Codex 原分叉内容由用户明确授权放弃

### 本次规则处理

- 原样合并：44 条。
- 修改后合并：1 条。
- 未合并：3 条。

修改后合并的是文件名称规则。最终文字同时覆盖 `CLAUDE.md` 和 `AGENTS.md`，并要求读取当前宿主加载的用户级规则文件。

本次未合并：

- `/tmp` 禁令：用户明确排除。
- 主动使用视觉功能的禁令：用户明确排除。
- 中文注释规则：用户明确排除。

这些排除决定只适用于本次实例。另一台机器必须根据用户决定重新分类。

### 本次验证结果

- source rules：修改前后 SHA-256 相同。
- 顶层规则：44 条原样合并、1 条修改后合并、3 条未合并、0 条检查失败。
- 应合并的非空原文行：65 行，缺失 0 行。
- Codex、OMP 和 canonical file 的 SHA-256 相同。
- Codex 与 OMP symlink 都指向 canonical file。

## 完成条件

应用本指南的工作只有同时满足以下条件才算完成：

- 已根据目标机器的真实结构找到全部相关指令文件。
- canonical file 的选择有验证依据。
- 每条 source rule 都有处理记录。
- 原文已经尽可能保留。
- 所有改写和排除都有明确原因。
- 目标文件中的独有规则没有未经授权被删除。
- 所有宿主入口经过验证。
- source rules 和原有 staged 内容没有意外改变。
- 最终审计表完整，所有确定性检查通过。
