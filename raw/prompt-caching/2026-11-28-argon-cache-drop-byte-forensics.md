# Argon 缓存掉点的字节级取证：238,770 → 0 与 102,728 → 51,527

> Source: 本机 Headroom 8787 完整消息录制（`HEADROOM_LOG_MESSAGES=1`），配合 OMP 会话文件与并发分支对照
> Collected: 2026-11-28
> Published: Unknown

## 一、录制方法

在 Headroom 启动脚本里设置 `HEADROOM_LOG_MESSAGES=1` 与日志路径，使每条请求同时记录客户端发出的 `request_messages` 与转发上游的 `compressed_messages`。日志文件权限 600，共记录到 115 条 `gemini-4-argon` 请求。

比较方法：对同一首条消息的相邻请求，逐条做规范化 JSON 字节比较，找出第一条不一致的消息及其首个不一致字段。共得到 110 组可比较配对；其中 105 组转发后保持完整前缀，3 组在早期消息处发生改写。

## 三、102,728 → 51,527 的具体改写

下标 241 之前的前缀完全一致；该条 `role: "tool"` 的内容被替换为占位符 `[shaken ~62 tokens — recover: local://36.log (region 1)]`，字节数从 294 变为 133。对应 OMP 会话条目的 `prunedAt` 为 2026-11-28T05:04:11.936Z，即手动 `/shake` 的原地改写。

缓存前缀在该消息处截断，只保住前面的 51,527 tokens；5 秒后的下一次请求恢复到 105,800 tokens。

## 四、并发分支对照

同一会话内塞入 700 行工具输出，压缩后再开两个并发分支，随后回到主线续接，共 8 次真实流式请求。Headroom 压缩节省 17,205 tokens；系统消息与那条历史工具输出在两个分支与主线里字节不变，缓存依次为 8,486、8,507、8,507、8,486、8,531 tokens。

结论：`--mode cache` 的并发分支处理不会改写既有前缀。

## 五、录制规模与清理

录制期间日志增长到 278,711,106 字节（约 279 MB），内容为完整对话明文。取证完成后已移除启动脚本中的录制环境变量，重启代理并删除该日志。Headroom 的 `RequestLog` 不记录 `tools` 数组与原始 HTTP 头，因此消息完全未变的那次归零，无法区分上游缓存逐出与非消息字段变化。

## 六、与 `/shake` 的关系

四次严重掉点里有三次伴随工具结果内容被原地替换；一次纯归零没有历史改写。这条分工说明：`/shake` 能解释部分掉点的落点，不能解释全部归零。

## 七、与保温器的交互（源码直读）

`shake()` 与 `dropImages()` 直接原地修改消息对象的内容并打上 `prunedAt`，重建会话上下文时复用的是同一个消息对象引用。会话层的缓存变更检测按对象引用比较，原地修改后两侧引用相同，检测返回未变更。

闲置压缩入口在裁剪前会取消保温器，手动 `/shake` 与 `/drop-images` 没有这一步。结果是保温器可能继续按改写前的快照发送重放。

该缺陷已作为上游 issue 提交，本地未打补丁。
