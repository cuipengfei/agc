## 原版字体结构：从 BerkeleyMono 换成 Ioskeley

0.9.8 与 0.9.9 均为 18 份内嵌字体。终端等宽字体为 `Ioskeley Mono Term`（weight 400）与 `Ioskeley Mono Term Medium`（weight 500），各 3 份副本，因此共 6 个描述符槽位。`fonts.py` 的实测输出（节选）：

```json
{"family": "Ioskeley Mono Term", "characters": 7564, "cjk": 0, "samples": {"中": false, "文": false, "你": false, "好": false, "日": false, "本": false, "語": false}}
{"family": "Ioskeley Mono Term Medium", "characters": 7564, "cjk": 0, ...}
```

对比 0.9.7 的 `BerkeleyMono Nerd Font` / `BerkeleyMono Nerd Font Medium`，两者各 `11217` 个字符映射。0.9.8 起字符映射收窄到 `7564`，CJK 仍为 0。

`analyze` 输出的 `panics` 字段是全部 `panicFunctions` 数量。时间分支数量只在按消息 `time not implemented on this platform` 筛选后单独统计，两者不等。

上表的数值来自各版本 `~/.local/share/tern-web-<version>-original/plan.json`，其 `inputSha256` 分别为 0.9.7 的 `fafe58c52cc837f81342139da7e147ec2bce25d750b65cdbe533cfd2fc3e65f1`、0.9.8 的 `1e47421edc41c4776d63c61a39d628891223ed05f90236830ff91bdc983da3f7`、0.9.9 的 `628f3299db8f904d64676aaeb043d93d62822ada8b6fe493aefdf1adbd155ff7`。「调用数」是 `callers` 数组长度，指直接调用该 panic 函数的函数个数，不含间接调用链。

0.9.8 部署记录 `~/.local/share/tern-web-0.9.8/PATCH.md:20` 曾写作字符映射 `11217`、时间函数 `30295`（17 处）与 `30296`（3 处）合计 20 处。该段是从 0.9.7 记录复制的旧值；同一 WASM SHA-256 的 `plan.json` 实测为字符映射 `7564`、时间函数 `31414`（19 处）与 `31415`（3 处）。本文以 `plan.json` 实测为准。

## 字体清单与合并分配

`font_manifest.py` 输出 6 条描述符，每条带各自的 slot：

```json
"fonts":[
 {"style":"Regular","slot":6975632,"expectedPointer":3912027,"expectedLength":1501964,"url":"./pkg/MapleMono-NF-CN-Regular-6975632.ttf","sha256":"a575f533481139875243926514a5883dda4f5d24d6bf8c57586d6e146f0dfeec","bytes":20564520,"characters":33091,"cjk":20976},
 {"style":"Bold","slot":6975656,"expectedPointer":5413991,"expectedLength":1499864,"url":"./pkg/MapleMono-NF-CN-Bold-6975656.ttf","sha256":"1f6369330d1e00daa05981ab4832dae9d9c1897553e0e0112964b44d1f572acd","bytes":20517832,"characters":33091,"cjk":20976},
 ...
]
```

三份 Regular 共用同一字体文件与同一个 SHA-256，三份 Bold 同理。`maple.mjs` 按 `style` 分组，每种字体只调用一次 `__wbindgen_malloc`，然后把同一个指针与长度写入该 style 的全部 slot。6 条描述符因此只占两份字体内存，避免三倍分配。

生成的两份 Maple 字体各含 `33091` 个字符映射，其中基本 CJK 字符 `20976`。装配后 `cmp` 复核：`pkg/client.wasm` 与 `pkg/client.js` 均与 `--official` 输入逐字节一致，`deploy-manifest.json` 记录 `mode` 为 `font-only`、`wasmUnmodified` 为 true。

## CI 测试作用域

GitHub Actions run `41332985434` 的 `behavior` job 失败在 `Run bun test` 步骤，结果为 `80 pass / 11 skip / 1 fail`，共 92 个测试。

根因：`.github/workflows/tern-maintain.yml` 的 `bun test` 步骤没有 `working-directory`，在仓库根执行，因此收集了 `omp/agent/extension-tests/deny-mnemopi-grep.test.ts`。该测试第 8 行从 `process.env.BUN_INSTALL`（回退 `~/.bun`）下的 `install/global` 解析 `@oh-my-pi/pi-coding-agent/extensibility/plugins/legacy-pi-compat`；Runner 只安装了 Tern 工具的依赖，解析失败。

修复为给该步骤加限定：

```yaml
      - run: bun test
        working-directory: tools/tern-maintain
```

修复后 run `41444309707` 状态 `success`。本地 `bun run test:receipt` 在 `tools/tern-maintain` 下运行同一套件，结果为 `91 pass / 0 fail`、10 个文件、`durationMs` `157190`。

`test:receipt` 脚本把测试输出写入 `artifacts/test-receipt.log`，再解析出 `{tests, pass, fail, files, durationMs, commit}` 写入 `artifacts/test-receipt.json`；解析失败时以非零退出，避免出现「测试通过但没有 receipt」。`tools/tern-maintain/.gitignore:2` 忽略 `artifacts/`，该文件不入库。

## 重启后的启动路径

机器重启后 `~/.local/share/tern-native-0.9.9/runtime-state/` 仍保留 `tern-daemon.pid`、`tern-web.pid` 与 `web-token`，但进程已不存在。`runtime.start` 在这三处都会受阻：PID 文件存在即拒绝启动；`pickTokenFile` 用 `flag: 'wx'` 创建 `web-token`，文件已存在会抛 `EEXIST`；`start` 没有 `tokenFile` 参数，无法指定外部认证文件。

可用路径是保留 `~/.config/tern/web-token`，清掉三个过期状态文件后手工启动：

```bash
rm -f ~/.local/share/tern-native-0.9.9/runtime-state/tern-daemon.pid
rm -f ~/.local/share/tern-native-0.9.9/runtime-state/tern-web.pid
rm -f ~/.local/share/tern-native-0.9.9/runtime-state/web-token
/home/cpf/.local/bin/tern daemon --socket /run/user/1000/tern/daemon.sock &
/home/cpf/.local/bin/tern web serve --listen 127.0.0.1:8378 \
  --token /home/cpf/.config/tern/web-token \
  --assets /home/cpf/.local/share/tern-web-0.9.9 &
```

`runtime.start` 与 `lifecycle.upgrade` 都通过 `spawnRedacted` 启动服务并把输出写入日志后脱敏；手工启动 `tern web serve` 会把带 token 的入口地址直接写到 stdout，凭据会进入终端记录。启动后应核对 `tern --version`、HTTP 状态与 pane 列表，不依赖进程存活推断认证有效。

上述 CI 修复与 0.9.9 部署均在 2026-11-02 完成；0.9.8 的部署在 2026-10-30。
