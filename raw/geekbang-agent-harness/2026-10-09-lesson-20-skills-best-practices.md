## 判断标准：可预测（Predictability）

技能存在的意义，是从一个随机的系统里挤出确定性。这里说的确定性，指的是每次跑出类似的过程，而不是相同的输出。一个整理会议纪要的技能，产出的结果每次都不一样，但它的行为应该是类似的，先做什么、后做什么、什么算做完，都是稳定的。反过来，一个技能这次帮你列提纲，下次直接写全文，第三次又跑去改格式，哪怕每次结果都还过得去，它也是不可预测的，也就没法交给别人用。

## 实践一：明确触发

### description 是唯一竞争位

技能元数据里的 description 就是触发器。description 是唯一常驻在上下文里的字段，也是唯一的竞争位。一个技能只有一个 description，而它可能要在几十甚至一百多个可用技能里被选中。大模型做的事，就是拿这段描述和当前请求比对，所以描述必须提供足够的细节，让它判断该不该选这个技能。

description 同时承担两件事：说清这个技能做什么，以及说清什么时候该用它。但是我们应该重点强调什么时候用，而不是这个技能能干什么。过度注重描述这个技能能干什么，是写 Skill 时最常犯的一个错误。

### 反例与正例

反例：description: 根据之前存在的周报，以及本周活动，帮助用户写周报。

正例：description: 当用户提到"本周做了什么""写周报""汇总一下进展"，或者到了周五需要交周报时使用。

第二个例子：

反例：description: 分析 Excel 文件。

正例：description: 当用户发来 .xlsx 文件、要求做数据透视表、画图，或者提到"表格里的数据"时使用。

### 描述撞车时写边界

一个 Harness 里两个技能的描述几乎一样，模型不知道该选哪个。

description（技能一）: 帮助分析数据。

description（技能二）: 帮助处理数据。

用户说"帮我看看这份销售数据"，两个描述都沾边，它只能随便挑一个。改法是把边界写进描述，尤其是"不该用在哪儿"这一句：

description（技能一）: 当用户要判断趋势、找异常、得出结论时使用，产出结论和图表。不要用于数据清洗和格式转换。

description（技能二）: 当用户要清洗、去重、合并或转换数据格式时使用，不要用于趋势分析和出结论。

这类问题平时不容易被发现。只有当两个技能装进同一个 Harness，或者你自己装到十几个技能的时候，才会看到它总在这两个之间摇摆，或者干脆两个都不选。

### 模型调用 vs 用户调用

包含 description 的技能叫模型调用（Model-Invoked）技能。技能提供 description，Agent 可以根据上下文推断来触发它。

把 description 摘掉，技能对 Agent 就不可见了。只有依赖用户输入技能名字，或在别的技能中明确指定技能才能触发。这种技能叫用户调用（User-Invoked）技能。

这么做的好处是消除了模糊性，完全使用我们希望的技能完成对应的操作。但是坏处是限制了技能自由度。

## 实践二：恰当的自由度

### 反对拿写代码的思路写技能

技能不是程序代码，大模型需要一定的灵活性来适应用户的具体语境和环境配置。过度限制自由度实际是拿写代码的思路在写技能。

举例：AI 短剧生成分镜图技能。硬编码 /generate-image 调用路径，假定用户一定有这个工具。用户可能无法访问该模型，也可能安装了其他技能提供不同的美术风格。改成文本指令"根据分镜提示词生成图片"，模型可以自己找到当前 Harness 里可用的图片生成方式。

### 三档自由度

按照 Anthropic 的最佳实践，技能可以有三种不同的自由度：

- 低自由度，特定脚本，参数很少或没有
- 中等自由度，伪代码或带参数的脚本
- 高自由度，基于文本的指令

### 重新映射到内层循环四环节

在双层循环架构下，内层循环是 Guides → Action → Sensors → Steering 四个环节，而自由度这个刻度，量的其实是这四个环节里有多少交给模型。

- 低自由度：四个环节全都由技能定好，模型只负责把 Action 执行掉。Guides 是逐字命令，Sensors 是确定的信号（退出码、固定输出），Steering 是失败就停。
- 中自由度：Guides 和 Sensors 定好，Action 里的选择交给模型。形状固定，内容自由。
- 高自由度：只定 Guides 的方向和 Sensors 的标准，Action 怎么走、Steering 怎么转，都交给模型。

不同任务对确定性的要求不同，选哪一档看这一步做错了能不能倒回来。

## 实践三：体积控制与拆分

### 先看结构再看数字

技能会自己变胖。虽然可以看到类似于"技能不要超过 500 行"之类的最佳实践，但是这并不是最好的控制方法。按照内层循环的四个环节过一遍，问题的位置和应对方法都会清楚得多。

首先是看四个环节有没有缺失。缺失比臃肿更常见，比如我们之前在坏味道里就介绍过反馈的缺失。

### 哪一环膨胀

然后再看看膨胀的是哪一环。前馈膨胀是不是出现了前馈痴迷的坏味道。而反馈膨胀是不是有反馈过载的问题。

Action 膨胀，通常是每一步都写成了逐字命令，本该给方向的地方也钉死了。这不只是长度问题，同时是自由度问题，压缩之前要先问一句这一步该不该定这么死。反过来，Action 里那些反复出现的机械操作，应该从一大段说明收敛成一个脚本调用，既简短又稳定。

Steering 膨胀，通常是异常分支被铺成了一棵决策树。解决办法是只留几条关键转向，什么情况停下、什么情况重试、什么情况升级给人。剩下的交给模型判断。

### 数字拐点

在确定结构没问题之后，再看数字。数字量的是总量，不是分布。正文控制在五百行、五千词元（token）以内，这是实测出来的拐点，超了要处理。

### 拆分判据

判断的主要依据是，能否提取一个独立的触发器。比如 AI 短片分镜图的例子，可以提取出编写分镜提示词以及根据提示词生成图片两个不同的触发器。那么自然不应该把它们俩合并在同一个技能中。

按照内层循环的结构判断，拆出来的技能，必须自己有完整的四个环节。如果拆出来的只是有 Action，那它不算一个新技能，只是一段被挪走的行为说明。同样，如果拆出来只有反馈，那就说明这应该是反馈分级中的一步，而不是独立的技能。

## 实践四：内层循环本身即是最佳实践

如果我们遵守双层循环的模式，内层循环本身就已经是一种最佳实践了。在此之上，我们再结合这一讲介绍的几个实践，配合知识固化，高效编写技能也并不是什么难事了。
