## 第 22 讲：内建质量——把验收做进循环里（article/1023771）

### 双层循环与人的分工

双层循环已经把能自动化的质量都自动化了：内层循环的前馈（Guides）和反馈（Sensors）贴着每一步自动检查进度并修正，外层循环的 Check 按 Plan 追踪整体进度。但「要解决什么问题？」「怎么算成功？」这类方向和标准问题机器判不了，也不该交给机器判。双层循环负责「做对」，人负责判定「什么是对的」。

### 五种介入方式

1. **完全介入**：人直接指挥每一步。
2. **动作前批准（Pre-Action Approval）**：有后果的动作先批，常规动作自动流转。拦的是「对外」这一下。
3. **提交前批准（Pre-Commit Approval）**：成果变持久、变可见之前要人批准，例如提交合并请求前看 diff。
4. **异常升级（Exception Escalation）**：只在策略、风险或者校准过的置信度越过阈值时才介入。
5. **完全自主**：事后审计，不中途拦截，适合有界、可逆、低风险、大量的动作。

### 橡皮图章与介入目标

介入不是越多越好。人工审核最常见的失败模式叫**橡皮图章（Rubber-Stamping）**：审批请求太频繁、太含糊、几乎总被批准时，人就不再仔细看。原文写道：「有一个被反复引用的数字：一个评审者每小时看到超过二十个审批请求，就会开始在超过九成五的请求上不看就批。」因此介入的目标是「更少、更高价值的介入」。

### 四个衡量维度与两个陷阱

- **可逆性**：能不能撤销，撤销代价多大。
- **外部性**：会不会影响 Agent 控制范围之外的人或系统。
- **价值**：多少钱、多少时间、多少信任押在上面。
- **政策**：法律、合同、安全规则要不要人过目。

通用原则：授权内的、有界的、可逆的、低风险的动作放手；不可逆的、外部可见的、高价值的、涉及政策的动作拦下来等人。

两个陷阱：① **可逆性不是免死金牌**——删掉的记录也许能恢复，泄露的密钥和发出的消息收不回来，所以先看政策、价值、外部性，最后才看可逆性；② **风险要算总账**——单笔小动作低风险，高频累计后可能变成高风险。

### 动作前批准与异常升级的工程实现

「高危操作先问我」不能只写进提示词，必须落在**工具网关（Tool Gateway）**：所有工具调用经过统一 `dispatch` 入口，按工具声明的审批等级做 `allow` / `ask` / `deny` 三态裁决。`ask` 挂起并向人展示做什么、为什么、代价、风险与过期时间；人拒绝时把拒绝原因作为返回值喂回模型。

异常升级用流程图分支上的临界值实现，最常用的是 AI 置信度；模型自报置信度普遍偏高，要先用带标准答案的样本集校准，再定阈值。

## 第 23 讲：Harness 的自我改进——以技能为资产、以 Eval 驱动（article/1024389）

### 四件事

1. **生命周期管理**：技能从一次失败里诞生，被反复使用，可能过时，最后该退役。
2. **验证**：技能不能写出来就采信，是另外三件事的核心，落地为给技能配备评估机制（Eval）。
3. **抽象**：存的是「怎么做这一类事」，不是「那次是怎么做的」。
4. **维护**：接口、场景、模型都会变，技能得跟着改。

### 三类评估信号

- **触发精度**：该触发时漏没漏，不该触发时误没误。很多技能的死因是 `description` 写得不好。
- **输出质量**：结果、步骤、风格对不对，考察前馈与反馈质量。
- **效率**：延迟、token、成本。**效率和质量必须成对看**，便宜但质量掉了不是净改进。

### 评估流程与净提升基线

1. 写用例：起步 10 到 20 条，每条配「什么叫做好」的标准，外加至少一条「不该触发」的相邻负面控制。
2. 跑：带技能逐条执行用例（原文还给出每条用例起独立会话防上下文串扰的做法）。
3. 检查打分：确定性检查（客观但覆盖面窄）与评分标准 rubric（灵活但可被刷新）两层互补。
4. 对比：既和上一次的分数比，也和**没带技能的分数**比，后者测的是「净提升」。如果摘掉技能后裸模型也全过，说明能力已被模型内化，技能应考虑退役。

## 第 24 讲：Loop Engineering——设计高效的控制循环（article/1024966）

### 演进三阶段

- **Ralph Wiggum（2025 年 7 月，Geoffrey Huntley）**：`while :; do cat PROMPT.md | claude-code; done`。每轮用全新上下文重启，任务、进度、下一步全部写进 `PROMPT.md`，模型记忆每轮清零而进度不丢。
- **Simon Willison（2025 年 9 月）**：把改 Dockerfile、部署到 Fly、测冷启动耗时封成三个技能，用 loop 让 Agent 自主计划、自主检测，利用内建自我纠正循环完成优化。
- **2026 年 4 月起**：Claude Code 加入 `/loop` 与 `/goal`，把循环构建成 Harness 内建标准模式。

### 外层 PDCA 到循环工程的映射

- **Plan → goal + 完成信号（done signal）**：把「要达成什么」写成可观察判据，如测试全绿、每个链接都能打开。
- **Do → 触发内层循环**：内层操控循环照旧。
- **Check → verifier**：把人为介入换成客观检查（exit code、测试结果、阈值）；在状态系统里记录循环轮次，避免死循环。
- **Act → stop / retry / escalate 规则**。

### 状态与五条停止条件

项目结构含 `plans/`（计划与完成判据）、`skills/`、`state/`（进度与轮次记录）。每轮向 `state/loop.md` 追加「第 N 轮 / 做了什么 / 检查结果 / 下一步」，只追加不覆盖；连续 N 轮「检查结果」和「下一步」与上轮完全一样说明在空转。

停止条件：① 完成信号成立；② 轮到上限还没完成；③ 连续 N 轮无进展；④ 范围外动作；⑤ 权限/认证/安全类错误（绝不重试）。

### /goal 的简化与边界

用 `/goal` 简化外层循环时，人只写 Check：完成条件（done signal）加轮次上限；Plan 和 Action 交还 Agent，Do 交给技能。完成条件越清楚，evaluator 越能替你判断。此做法只适合简单任务；像背单词这样需要复杂进度控制的 Harness，仍需自己编写外层循环。

## 第 25 讲：多 Agent 编排（article/1025999）

### 成本与适用边界

多 Agent 和微服务一样，用「拆」换「隔离」和「并行」，但每多一个 Agent，就多一处可能失败的地方、多一套要维护的提示词、多一次交接时的信息丢失。原文引 Anthropic 观察：有团队花好几个月搭精细多 Agent 架构，最后发现把一个 Agent 的提示词改好一点，效果就一样；**多 Agent 的 token 消耗通常是单 Agent 的 3 到 10 倍**。

只适用于三类场景：**严格工作流**（模型只在节点上发挥作用，不统筹全局）、**多路并发**、**上下文隔离**（在不同上下文窗口内独立思考）。为了「看起来高级」而拆，是交「嫉妒税（某某-Envy）」。

### TradingAgents 四层流水线与交接原则

1. 分析师团队：基本面、情绪、新闻、技术四路并行，报告交齐后进入下一层。
2. 研究员团队：多头与空头研究员针对发现做结构化辩论，产出平衡的市场判断。
3. 交易员：综合报告决定买/卖、时机、仓位。
4. 风险管理团队加基金经理：评估敞口、波动率、流动性，基金经理批准或否决。

整条流水线里**绝大多数信息是结构化输出**，只有研究员内部的多空辩论和风控讨论用自然语言对话。结构化输出能防幻觉、防信息丢失；辩论必须靠对话才能碰撞出相反观点。取舍原则是「该结构化就结构化、该对话才对话」。

### 两种轻量替代

- **状态文件 + `/loop`**：把 Agent 之间的结构化消息换成状态目录里的文件，把流水线先后换成文件依赖。示例状态目录：`state/analysts/{fundamentals,sentiment,news,technical}.md`、`research.md`、`decision.md`、`approval.md`。四层变成四个并行 loop → 一个辩论 loop → 一个决策 loop → 一个审批 loop；代价是 `/loop` 轮询的触发时机没有自主编排准确。
- **Subagent**：主会话派生独立 Agent，有自己的上下文、工具列表、模型，干完活只把最终结果交回主会话。Claude 用技能元数据 `context: fork` 表示该 skill 由 Subagent 执行；写两个 skill 分别在两个 Subagent 并行查不同数据源，就已经是多 Agent 系统，无需额外协调器。

## 第 26 讲：构造内部 Harness（article/1026795）

### 第一原则与三个差异点

所有 Agent 系统的内部核心都是自我纠正循环（Self-Correction Loop），即内部 Harness，软件架构高度趋同。因此**构造内部 Harness 的第一原则是：不要构造内部 Harness**，关注点应在外部 Harness 的四个子系统。

趋同不等于完全一样，剩余差异集中在：① **循环行为**（何时停、失败怎么重试、上下文快满怎么压缩、多任务怎么调度）；② **上下文取舍**（进什么、压什么、长期保留什么）；③ **工具执行策略**（审批、超时、并行）。只有当其中某一件与手头任务明显冲突时，才值得改内置机制。

### DeepSeek Harness 的五个可替换环节

DeepSeek Harness 的设计原则是一切皆插件（Cordis 插件框架），可替换环节为：① **agent loop**；② **工具流水线**（allow/deny/ask 审批 → 执行 → 结果替换检查）；③ **会话日志**（铁律「模型可见即已记录」，只追加不覆盖，日志是状态唯一真源）；④ **系统提示词组装**；⑤ **模型适配**。

### Agent loop 的三个扩展点与循环外步骤

- **pre-step**：每步开始前放行、拒绝或改写输入。例：只读代码审查 Agent 在此硬拒绝写操作，把「只读」从软性叮嘱变成硬性闸门。
- **request**：请求发给模型之前决定路由与提示词片段。例：普通工单走便宜模型，出现「投诉/赔偿/退款」时切到更强模型并塞入赔付规则。
- **turn-stopping**：轮次快收尾时再拦一下。例：本轮动过 `.py`/`.ts` 文件就塞一条「先跑相关测试，绿了再收尾」。
- **循环外新增步骤**：如 Hermes 的自我改进（self-improving），任务完成后回顾过程、自动提取 skill，改变下一次怎么开始。

### 外层循环固化进代码

当外层规则足够稳定、足够高频，可把它从提示词挪进 agent loop。例如「连续三轮没有任何进展，就停下来、升级给人」写进 `turn-stopping`，变成每次轮次收尾都执行的硬逻辑。收益是更准确（程序保证，不靠模型记住）和更高效（省掉每轮重复解释）。前提是内置循环确实不满足需求、频繁出错；能执行好就留在提示词里。

## 第 27 讲：Agent First Workspace——使用外部 Harness 的基准模式（article/1027541）

### 四种缺失与前置原则

人打断 Agent，几乎总发生在四样东西缺失时：① 知道要做什么（目标、规格、验收标准）；② 知道「这里是怎么做事的」（约定、环境、工具、风格）；③ 知道当前状态；④ 知道什么时候停。

第一原则：**把一切本来要在「运行时」人回答的东西，提前写成工作区里的工件，让 Agent 去读取，而不是去问。** 人的角色从「任务执行过程中的应答者」改成「任务开始前的规格作者」。最大化自主性不是去掉人的判断，而是把人的判断前置、固化、可复用。

### 知识库的四个来源

Agent 知识库装的不是人知道的东西，而是**让知识变得可获得的机制**：

1. **人写的**：地图、约定、意图。人写的是「到哪里去读」，不是「读到的内容」。复述会滞后、会腐烂，地图不会，因为地图指向活的源头。
2. **系统里本来就有的**：代码、配置、git 历史。最准确的事实来源是代码本身；这一层几乎不产生新文字，只把 Agent 引向唯一可信的源头。
3. **Agent 派生的**：探索、索引、结构、摘要。代码一变，重跑一遍索引，知识库随系统自动生长。
4. **Agent 沉淀的**：决策、踩坑、纠正。就地写回知识库，「每一个问题只需要被解决一次」；人认可的沉淀成果可升级进「人写的」层，成为新的锚定范例。

回归测试例子中，最值钱的输入（最近修过什么 bug）只在 git 历史里；产出的财富（坑、范例）又流回知识库喂给下一轮。

### 两段式下发任务

先下**设计令**：人给任务说明，Agent 根据知识库和流程出设计和方案；不满意就调整任务说明、增加反馈和验收条件，直到满意；再让 Agent 出详细 todo 和计划，人在计划中增加或撤掉人为检查点。再下**执行令**：Agent 进 loop 开始工作。审设计是人的判断成本最低、价值最高的位置。

## 第 28 讲：这门课的 Harness 如何构建（article/1028270）

### 三类目录与提纲/正文分离

写课 Workspace 分三类职责：

- **知识库**：`knowledge-engineering/`（前一门课原稿作风格锚定）与 `docs/summaries/`（行业资料摘要索引）。
- **产出物**：`outlines/`（提纲）与 `lessons/`（正文）物理分开，防止随时推翻的提纲污染正文。
- **Harness**：`AGENTS.md`（地图）与 `skills/`（流程）。

### 知识库的两个用途

一是**交叉验证**：核对课程方案是否仍最优。作者举例，文献中的 `progress-mirage`（进度幻象）坏味道因与已有坏味道重合而未纳入课程。二是**替换实例**：把不便公开的客户案例换成行业公开案例（如 TradingAgents）。

### 九步写作流程与人的位置

前四步是外层循环：确认讲号 → 读知识库与相关资料 → 写提纲 → 作者确认。五到八步是内层循环：写正文（每讲约 3000 字）→ 自查字数与重复 → 作者批示 → 按批示修改。第九步收尾：git 提交并生成 PDF。

可自主的五件事：自动获取知识更新、按更新审阅完稿、建议新主题、找正反面例子、判断内容重复。核心立意与审稿判断仍由人完成——把人不可替代的判断安放在成本最低、价值最高的点上。

## 第 29 讲：遗留系统上的 Harness 驱动开发实践（一）（article/1029430）

### 业务完整前提不成立，锚在代码上

遗留系统的业务目标、场景、规则要么分散在不同系统，要么随人员更替消失；试图先把业务补全再开工几乎走不通。**真正还完整留在手里的只有代码本身**。AI 读代码能了解「系统在做什么（What System Does）」，对「系统是什么（What System Is）」只能推测。代码里「看不懂」的判断、补丁、与业务对不上的逻辑，正是丢失业务信息留下的影子；业务背景只能作为帮助理解代码的补充说明，而不是知识库的地基。

### 按架构压缩与面向 Agent 的边界索引

面对代码库，压缩的最好方式是**按架构来压**：架构把几十万行代码筛掉实现细节，压缩成「系统分成几块、每块负责什么、块之间怎么连」的骨架，信息密度最高也最稳定。**骨架常驻，细节按需读入。**

知识库应从 Agent 角度而非人的习惯构造。微服务内部的 clean code 分层是为配合人脑有限认知；Agent 一口气能读完单个微服务，内部那几层随时可回原代码重读。Agent 的短板在**服务之间的边界与交互**：功能归哪个服务、服务怎么通信、数据归谁、改一处波及哪。索引应保留每个服务的职责、服务间调用关系、数据所有权；压缩要压掉 Agent 能随时重新获取的，留住 Agent 拿不到的。

### Workspace 与三 Skill 链

独立 workspace repo 的结构：`AGENTS.md`（入口地图、约定、意图）、`skills/`、`checkout/`（由 Agent 托管 clone/pull 各业务仓库）、`wiki/`（知识库）；`repository.md` 列出全部 repo。

1. **`repo-index`**：读 `repository.md`，产出 `wiki/index.md`，回答系统有几个 repo、各自大致做什么。README 只当线索，代码为准。
2. **`api-contracts`**：为每个服务产出提供的 `api.spec.md` 与消费的 `api.contract.md`；识别不出的标「待确认」，不猜。
3. **`service-map`**：把所有 contract 中的 API 与所有 spec 对照、反查提供方，拼成带 API 标注的 mermaid 依赖图；对不上的画虚线标待确认。spec 与 contract 是同一份契约的两半。

作者实际项目为 78 个 repo，每天知识升级约 35–40 分钟。

## 第 30 讲：遗留系统上的 Harness 驱动开发实践（二）（article/1029982）

### 任务驱动的知识提取

spec/contract 记录的是「接口长什么样」；回归测试要测的还有接口背后的行为。知识是为任务服务的，任务没发生时没法预知用到哪一块，因此**知识提取的正确姿势不是提前囤够，而是任务驱动**：拿现有知识先试，缺口暴露后回代码和业务注释里补，补完这一块知识库就长大一点。

### implement-flow：行为知识与调用链

`implement-flow` 从 `api.spec.md` 的每个 HTTP endpoint 出发，顺处理函数记录：调了哪些下游 HTTP API（标目标服务和路径）、查/写了哪些数据库表、发/收了哪些消息队列、关键分支条件；每个 endpoint 在 `wiki/{repo}/endpoint-flows.md` 画一张 mermaid 调用链。

这张调用链是**几乎无损的上下文压缩**，也是现成的回归测试提纲：正常路径、每个分支（「是」和「否」都测）、每个下游调用的失败/超时/异常、每个落库点，都是该测的路径。

### 探针测试与反向校准

`test-case-design` 读调用链逐项提取测试案例；**「待确认」节点设计「固化现状」的探针测试，列为最高优先级**。`test-implement` 只加测试、不改生产代码，mock 写法照抄仓库现有模式。

探针测试跑挂了**不是 bug，而是信息**：说明系统现状与推测不符。把实测出的真实行为**回写进 `endpoint-flows.md`**，知识库由此被测试反向校准；不给断言放水、不把待确认写成既定事实。

### AGENTS.md 升级为能力清单

在工作区入口写清每类任务怎么触发、走哪条 skill 链、产出什么文件，例如「补回归测试 → `implement-flow` → `test-case-design` → `test-implement` → 回写知识库」。入口从「目录说明」升级为「能力清单」，人和 Agent 都知道这个 Workspace 能干什么。

## 结束语（article/1030948）

- 课程核心不是现成代码库或一个万用 Skill；重构与 Harness 的重点都是**过程与判断力**，不是改完的结果。
- 双层循环里人的位置：**Guides 是人的**（意图、标准、约束给足），**Steering 是人的**（根据反馈做转向判断），**Action 是 Agent 的**，**Sensors 尽量交给机器**（能自动检查的就不用人盯着）。结构本身不是重点，如何分割内外层循环边界并结合子系统设计才是重点。
- 第二部分（坏味道）更像 debug：把「Agent 让我失望」这个模糊信号落回具体环节——需求没说清、没建检查、状态被弄脏、环境变了等。十三个坏味道是十三种常见病因；从现象找到根因的能力通用且带得走，而诊断恰是人的判断力里最没法替代的部分。
- 原文结尾判断：**「把判断外包出去，不是驾驭，是缴械。」** 人从「亲手做每一件事的执行者」变成「决定该做什么、判断做得对不对的驾驭者」。「让 AI 代替我们执行，而不是代替我们思考。」
- 注：结束语原文没有「三层闭环」这一术语。
