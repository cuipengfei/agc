## 为什么 Agent 拿通用方案套项目上下文？（08，article/1012725）

隐式约定（Implicit Convention）：Agent 不了解不同模块实现方式的约定，在拿通用方案套你的项目特有上下文。不是 Agent 猜错了需求，而是它对于解决问题的约束存在不同的理解。

与模糊需求的区分：实现方式的澄清需要处理不同的优先级。不同模块因历史原因有不同的权衡，A 模块走中介层是因为两年前出过数据一致性问题，团队在「性能优先」和「一致性优先」之间选择了后者。

重构手法是建立原则文档（Establish Principles）。原则文档不是规则清单——规则清单告诉你「怎么做」，原则文档告诉你「当 X 和 Y 冲突时，优先选哪个」。它不是给 Agent 一本「每个模块该怎么做」的操作手册，而是给它一套决策框架。

文件结构三层：

- AGENTS.md 是入口层：引用原则文档的位置和用法，保持简洁
- docs/constitution.md 是原则层：全局红线、规则、建议，每条带原因（Rationale）
- docs/decisions/adr-*.md 是模块层：模块级 ADR，记录上下文、决策、权衡、影响

五个优先层级（从高到低）：

1. 不可协商的红线：安全合规、数据保护、法律要求，任何情况下不能违反
2. 用户当面的指令：能覆盖项目级规则和模块级权衡，但不能覆盖红线
3. 项目级约定：AGENTS.md 和原则文档中写明的全局规则
4. 模块级约定：模块级 ADR，记录不同模块各自的权衡
5. 最佳实践：通用建议，上下文冲突时可以灵活让步

诊断信号：Code Review 时反复说「这里应该用我们约定的方式」；Agent 迟迟无法完成功能因为在从头发明解决方案。

## 为什么文档比没有文档更糟糕？（09，article/1013301）

信息散落（Scattered Information）：知识被纳入仓库后，因为更新不及时，导致仓库里的信息不再是事实本身，而是事实的旧版本。这比没有文档更糟糕。

没有文档的时候，Agent 至少知道自己在猜，输出带有不确定性，你会检查。有文档但过时的时候，Agent 自信地执行错误的信息，而且这份自信来自你建立的仓库。

根源：仓库里的信息是静态的，而现实是动态的。仓库和现实之间的差距每天都在扩大。

重构手法是管理知识依赖。仓库中的每条信息都是一条知识依赖，依赖某个外部信息源（团队 Wiki、会议决议、邮件、第三方文档等）。当外部信息源变化时，就要及时更新。

两种落地方式：

- 有 URL 或 API 的来源：建立 SOURCE.md 文件，列出仓库文件、外部来源、更新时机；构造一个 Skill 从对应来源拉取最新内容，有差异则自动更新
- 没有固定来源的：在 AGENTS.md 中增加提醒环节，每次会话开始时 Agent 主动询问用户是否有更新

工具：OpenWiki（LangChain 开发的 CLI 工具），内置 Gmail、Slack、Notion、X/Twitter、Web Search、Git 仓库等连接器，自动吸入信息。少量信息源用手动方案（SOURCE.md + 定时 Skill），多而频繁变化的用 OpenWiki。

核心原则：知识依赖管理是 Harness 的标配组件，不是可选项。

## 为什么 Agent 来回横跳修不好？（13，article/1016964）

反馈过载（Feedback Overload）：反馈（Sensors）太多，反馈信号互相淹没。测试、lint、类型检查全失败，Agent 无法确定优先修复哪个；大量输出灌满上下文，Agent 丢失任务目标。

成因：反馈信号没有分级。所有反馈一视同仁地输出。一个「数据引错了」的硬伤和一个「语气不够活泼」的风格偏好，在修改意见里看起来差不多。分级一直存在我们心里，却没有写出来。

重构手法是分级反馈（Grade Feedback）。核心思想不是减少 Sensors，而是给反馈分级：不同严重程度的信号用不同的呈现方式，让 Agent 一眼看出「先修哪个」。

第一原则：成功静默，失败才输出。全部通过时不输出任何东西，或者只输出一句「全部通过」；只有失败时才输出信号。

按严重程度分三级：

- 阻塞级（Blocking）：不修就无法工作的错误，比如编译失败、测试挂掉。最高优先级，输出完整信息
- 警告级（Warning）：应该修但不阻塞的，比如 lint 风格问题、潜在风险。次之，摘要输出
- 信息级（Info）：可忽略的，比如成功消息、普通日志。默认静默，需要时才看

分级的依据是反馈对任务目标的威胁程度。阻塞级对应「不修就不能交付」，警告级对应「应该修但不影响交付」，信息级对应「不影响结果」。

分级的实质是责任分界：阻塞级是模型必须完成的；警告级由模型评估后，人来决定是否继续完善；信息级通常可以转化为前馈。三层足够，分更多级只是把反馈过载换成另一种形式。

分级反馈的额外好处是节约 token：Agent 首要目标只有满足阻塞级的要求，收敛需要的轮次变少，每轮处理的信号也变少。

诊断信号：Agent 耗费很长的时间尝试让最终结果符合全部的反馈要求，修改行为「看起来在动，但没有方向」。

## 为什么状态存在但不可信？（17，article/1020113）

状态污染（State Pollution）：本该随任务结束一起消亡的执行数据，混进了要跨会话复用的状态里；读取方无法分辨，就把这些执行数据当成固定知识来用。临时内容被当成了长期事实，状态失去了可信度。

两个典型来源：工具给出误导的结果（「练习完成」其实 0 个词）；模型自己过度推断（一次用了虚拟式就认定「已掌握」）。

根源在单 Agent 架构：一个会话既要执行，又要记录执行过程，两者共享同一个上下文。执行过程中的调试痕迹、中间产物、临时判断、产生的幻觉，和要长期保留的进度、决策、知识，没有一道边界隔开。

重构手法是状态分区（State Separation）。核心思路：把状态按生命周期分成两类——随任务消亡的临时状态，和跨会话复用的持久状态。执行数据只许落在临时状态里。

两种分区方式：

- **草稿纸（Scratchpad）**：容器和渠道上分离。给执行数据单独划一个区域，一块随任务消亡的临时工作区。草稿、中间产物、调试观察、工具返回的原始结果、还没验证的结论都写进草稿纸。收尾时先做整合（consolidation），把值得保留的内容提炼成带来源的知识条目，剩下的随草稿纸一起销毁。整合不是在草稿纸里挑挑拣拣，而是对每一条内容重新做一次判断：这条到底是知识还是执行数据；如果是知识，它的依据是什么。
- **双层循环**：结构上分离。内层循环每执行一个子任务就开一个短命会话，任务结束会话销毁，执行数据从结构上就到不了持久状态。外层管状态，内层没有直接写持久状态的通道。审视者与执行者分离，外层对照真实情况核验内层产出。Check 环节是天然的整合点。

关键判断：出现状态污染，往往说明任务复杂度已经超过当前 Harness 架构能处理的范围。与其只想着治污染，不如检查架构与任务是否匹配。

## 为什么 Agent 昨天能跑今天就不行了？（18，article/1020522）

环境漂移（Environment Drift）：Agent 运行所依赖的条件没有被显式声明和锁定，却在悄悄变化。每次运行的条件都不一样，行为不可复现、错误无法定位。

环境四类：运行时（操作系统、语言版本、shell）、依赖（第三方库精确版本）、外部服务（API、数据库）、模型（厂商可能同名换版本）。

漂移两个场景：时间上的漂移（API、模型随时间改版升级，同一台机器上行为悄悄变了）；空间上的漂移（依赖、shell、操作系统因机器而异，换台机器就失效）。

重构手法是环境锁定（Lock Environment for Agent Harness）。核心思路：把隐式的、会漂移的环境变成锁定的、可复现的环境，用的是软件工程里成熟的 lockfile 范式。

四个落地步骤：

1. **init.sh**：初始化精确的文件夹结构、配置文件和初始状态
2. **lockfile**：锁定运行时与依赖的精确版本（.nvmrc、package-lock.json、requirements.txt、pyproject.toml 等）
3. **Skill 局部化**：第三方 Skill 安装到项目内部的 skills/third-party/ 目录，锁定版本（tag 或 commit），写进 AGENTS.md，初始化时校验版本一致性
4. **MCP 间接层**：外部服务的改版交给 MCP 服务器吸收，Agent 的调用逻辑不动。完成局部化后可打包成 Docker image 分发

作者明确反对通过自我纠正机制在生产环境做 Monkey patching 来应对第三方 API 变化。

## 为什么 Agent 总在抄你最想淘汰的代码？（19，article/1021042）

模式复制漂移（Pattern Copy Drift）：仓库里既有的产物本身就是 Agent 的学习材料，它会把自己读到的模式复制下去，不管这个模式是不是团队正打算消灭的。

三个成因：

1. **训练目标奖励「接得像」**：代码模型的训练目标是给定上下文预测下一段代码。写得和仓库里周围的代码一个样，在训练目标上是得分的。随着模型规模增强，大模型会放弃预训练里的先验，转去跟随上下文里的示例。
2. **指令与范例冲突时范例权重更高**：随着示范数量增加，模型会从遵守指令逐渐转向跟随示范。AGENTS.md 里的约定是几条，仓库里的旧模式是几十上百个示范。
3. **检索排序把旧代码排前面**：Agent 写代码时先检索当前实现，按相关度排序。排在前列的正是实现同类功能的旧代码。

重构手法是模式基线化（Pattern Baseline），分四步：

1. **正向范例**：给出新写法的样子，放在仓库固定位置，在 AGENTS.md 里指路。使用独立的参考实现，不用项目中实际的代码
2. **确立架构约束**：把约定变成会失败的自动化检查（自定义 linter 或 ArchUnit）。原则：强制不变量，不微观管理实现
3. **建立基线**：现存违规记录进基线文件，只许减少不许增加
4. **持续清理**：任何改动碰到存量代码，就在这次改动里按新模式重新实现

前两步的分工：范例告诉它该照着谁写，约束让照着旧的写就失败。一个给方向，一个给边界。

顺序有依赖：先有范例，约束才拦得对；先有约束，基线才有东西可记；先有基线，约束才敢上线。
