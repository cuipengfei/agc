# 一次配置任务的范围蔓延与恢复：可复用的边界纪律

> Source: 2026-11-28 本机会话记录与仓库状态核对
> Collected: 2026-11-28
> Published: Unknown

## 一、发生了什么

用户要求只改 OMP：为同一网关的现役 GPT 配置缓存保温，并清理 OMP provider 中已退役的模型与直接引用。

执行中把「同一来源的配置」理解成一起改，向子任务描述了 OpenCode、Prime、OMO 三个宿主的同类清理。停止指令到达前，这些仓库副本与部分来源文件已被修改。

## 二、恢复过程

- 仓库副本：`git show HEAD:<path>` 取出任务前原文，用文件编辑工具整体写回。涉及 5 个仓库文件（OMO 两个、OpenCode 一个、Prime 两个）。
- 来源文件：在模型块区域内点对点逆编辑，保留各自原有的凭据与本地差异。
- OMO 仓库副本里的 48 处角色引用逐字段回填为原值。
- 核对结果：`git status --short -- omo opencode prime` 无输出。

## 三、未解决项

Prime 来源里的 `c8787-chat` provider 在恢复时重建，其 `apiKey` 复制自同文件的 `c8787` 条目。任务开始前没有该 provider 的凭据指纹，仓库副本里两个条目都只有脱敏占位符，因此无法证明两者原本相同。

这一处保持现状并记录为未解决，没有继续猜测或改动。

## 四、纪律

**派发子任务时把用户的边界写进任务描述。**「同一来源」「同源配置」不是扩展授权；用户点名哪个宿主，就只动哪个宿主。

**恢复自己的误改，仓库里被 git 跟踪的副本就是可靠基线。** 用 `git show HEAD:<path>` 读原文再写回，比回溯会话记录里零散的编辑片段准确得多。git 在这里只作只读引用，不执行回滚命令。

**长等待实验在关键判定第一次失败时就该停。** 保温重放首次未命中后还继续等满 40 分钟，剩余时间只会得到一个已知的结论。

**统计库的字段不能直接当作事实分类。** `agent_type` 为 `main` 的记录里混有输入预测等辅助调用，必须用原生解析器读条目类型区分。

**测保温要在用户实际使用的链路上测。** 同一模型、同一参数，经代理与直连绕过代理给出相反结果；换一条链路测出来的结论不能直接搬用。

**耗时长的部分先给结论再继续。** 用户中途问进度时，先说清当前到了哪一步、还剩什么，比继续埋头执行更有用。
