# RTFM

RTFM 即 **Read The Fucking Manual**：别在本地瞎猜试错，也别脱离本地代码只顾着在网上乱搜。像真人排查一样，拿着手头的线索在官方资料和本地代码之间来回核对，对上号再动手。

用户说出 RTFM，或者模型准备查文档、翻本地代码时：

1. 停下凭空猜测、盲改代码试错、monkey patch 和来回换版本。读本地报错、配置和代码是正常取证，照常进行。
2. 顺着线索在官方资料和本地代码之间来回查（用户指定了文档、来源或工具时，先用用户指定的）：
   - **先从现场拿准词**：看一眼报错、依赖文件、配置文件或出问题的那几行调用，拿到准确的包名、版本号、配置键、函数名或报错原文，别靠印象去搜。
   - **带着词去查官方文档**：用刚拿到的名字和版本号去查官方文档、CLI `--help`、Context7、release notes、registry metadata 或上游源码，弄明白当前版本里这个库或工具怎么用、怎么配、有什么限制。
   - **拿着官方说法回本地核对**：查清官方要求后，马上回到本地的配置文件、`AGENTS.md`、CodeGraph、本仓源码或日志，看本地实际怎么用、怎么配，跟官方文档说的差在哪。
   - **本地冒出新疑问再回头查文档**：看本地代码时要是又碰见拿不准的接口、参数或报错，就拿新线索再去查一轮官方资料。不知道官方怎么用就查文档，不知道本地现在什么样就看代码，两边对上了就停下检索。
3. 必须读到和问题直接相关的文档正文或源码，光看搜索标题和摘要不算查完。
4. 一处没查到就换个入口；有工具能查就自己查，别让用户代劳，也别靠猜测补全未知事实。
5. 动手改之前，先写清已经核实的事实、还没查清的地方、原因判断、最小改动和验证办法。
6. 牵扯多个变量时分开验证，优先在隔离环境里试；只有证据对上了才改本地代码或配置。

完成标准：结论中涉及的官方用法和限制有读过的权威资料支撑，涉及的本地现状有核实过的代码或配置支撑，本地改动有明确依据和可执行的验证办法。
