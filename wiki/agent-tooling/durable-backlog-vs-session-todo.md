## Overview

Coding agent 通常自带会话内的 todo 工具，外部任务系统 `bd` 又提供持久任务库。两者记录的不是同一层的东西：todo 是本次会话的执行步骤，`bd` 是跨会话、跨 agent、跨机器的交付项与依赖图。选择按生命周期、共享范围、依赖关系、粒度和审计需求判定，避免同一件事在两边重复记录。

## OMP todo 的边界

OMP 的 `todo` 工具有 `init`、`start`、`done`、`rm`、`drop`、`block`、`unblock`、`append`、`view` 这些操作。工具说明要求：

- 多步任务先初始化阶段与条目，3+ 步时使用。
- 任务用原文内容标识，不用生成的 ID。
- 同一时间只保留最早的活动任务。
- 外部等待用 block，解除后回到 pending。
- `todo` 不能单独占一轮，必须和真实动作一起发出。

它记录当前会话接下来怎么做，工具说明没有提供跨会话持久化，也没有导出到项目仓库的接口。会话结束或新开会话后，这套清单不再承担项目记忆。

## bd 的边界

`bd` 把任务存进项目里的 `.beads/` 数据库，Dolt 提供版本历史，任务之间可以声明阻塞依赖。`bd ready` 计算没有活动阻塞的任务，`bd update --claim` 领取，`bd close` 关闭；数据可以推到同一个 Git 远程的 `refs/dolt/data`，供其他机器与其他 agent 拉取。

它适合这些内容：

- 跨会话、跨上下文压缩仍然要保留的交付项。
- 多个 agent 共享的任务池，需要领取与依赖关系。
- 需要关闭原因、评论、历史审计的任务。
- 属于仓库、应随代码一起共享的计划。

## 选择规则

按顺序判断，前一条成立就停止：

1. 这项工作要不要活过本次会话？要，用 `bd`。
2. 其他 agent、机器或人要不要看到？要，用 `bd`。
3. 需不需要依赖关系和 ready 计算？需要，用 `bd`。
4. 这是交付项还是执行步骤？交付项用 `bd`，执行步骤用 `todo`。
5. 需不需要关闭原因、评论、历史审计？需要，用 `bd`。
6. 用户说“记下来，以后做”还是“现在做这几步”？前者用 `bd`，后者用 `todo`。

| 场景 | 选择 |
|---|---|
| 本次会话的多步执行计划 | `todo` |
| 跨会话、跨机器的 bug 或 feature | `bd` |
| 需要依赖图与领取 | `bd` |
| 一次调查、验证、跑测试 | `todo` |
| 多个 agent 并行，避免抢同一条 | `bd` |
| 把交付项拆成执行步骤 | `todo` |
| 把交付项拆成可独立领取的子项 | `bd` |

## 混合流程

1. 会话开始，检查项目里有没有 `.beads/`；有就运行 `bd prime` 或 `bd ready --json`。
2. 选一条持久任务，`bd update <id> --claim` 领取。
3. 针对这条任务，用 `todo init` 建本次会话的执行步骤；步骤文本带上 bd ID，例如 `bd-a1b2: 改解析器`。
4. 执行时由 `todo` 记录下一步；阶段性状态写回 `bd`，用 `bd comment` 或 `bd update`。
5. 交付项完成时 `bd close <id>`；`todo` 清单随会话结束丢弃。
6. 不把每个 `todo` 步骤都写成 `bd` 任务，也不把跨天工作只放在 `todo` 里。

这样 `bd` 是状态与完成判定的唯一来源，`todo` 只承载当前交付项的执行顺序。

## 反模式

- 同一粒度同时写进 `bd` 与 `todo`，两边状态迟早不一致。
- 把 `bd` 当成会话日志，每个读文件、跑测试的步骤都建一条任务。
- 只维护 `todo`，会话结束后跨天工作全部丢失。
- 用 `bd` 记录一次性的调查步骤，任务库被临时条目填满。

## 在 AGENTS.md 中固定规则

规则写清楚后，选择由文本决定，不靠模型临场判断：

> 持久工作项放在 bd；本次会话的执行计划用宿主 todo 工具；todo 文本携带对应的 bd ID；bd 是状态与完成判定的唯一来源；不要为同一个步骤同时创建 bd 任务和 todo 项。
