# 配置类任务的范围控制与恢复基线

## Overview

一次「只改 OMP」的配置任务被扩展成三个宿主（OpenCode、Prime、OMO）的同类清理，停止指令到达前已改写仓库副本与部分来源文件。恢复靠仓库里被 git 跟踪的副本作基线，48 处角色引用回填原值，仓库状态回到任务前。一处凭据对应关系无法证明，保留为未解决。

## 边界要写进任务描述

「同一来源」「同源配置」不构成扩展授权。用户点名哪个宿主，就只动哪个宿主。

派发子任务时，把这句话写进任务描述本身。子任务看不到主对话，它只按收到的文字判断范围；「清理本机相关 provider」这种表述会被合理地读成全部同类宿主。

## 恢复用仓库副本，不用会话记录

仓库里被 git 跟踪的副本是任务前的可靠基线。`git show HEAD:<path>` 读出原文，再用文件编辑工具整体写回，一次到位，不依赖回忆或零散的编辑片段。

来源文件不能整体覆盖，里面有自己的凭据与本地差异；在受影响的块内点对点逆编辑即可。

本次恢复了 5 个仓库文件与对应来源文件，48 处角色引用逐字段回填，`git status --short` 对那三个目录无输出。

## 无法证明的地方要说明

Prime 来源里一个 provider 在恢复时重建，其凭据复制自同文件另一条目。任务前没有该条目的凭据指纹，仓库副本里两处都只有脱敏占位符。

这种情形记录为未解决，不用推断填补。

## 长等待要设停止条件

保温重放的首次判定失败后，剩余等待只会得到一个已知结论。实验设计里给每个阶段设一个「判定失败即停」的条件，比给一个总时长更有效。

## 统计字段不等于事实分类

本机用量统计库把输入预测等辅助调用也记成主会话。辅助调用会真实发往上游并可能刷新缓存，把它当普通对话样本会系统性高估缓存存活。

同一份数据里，`agent_type` 为 `main` 的 5,630 条记录中有 203 条其实是辅助请求。判断样本身份要用解析器读条目类型。

## 测性能要固定在真实链路

同一模型、同一参数，经代理与绕过代理给出相反结果。测保温就在用户实际使用的链路上测。
