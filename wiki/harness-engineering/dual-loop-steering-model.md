## Bad Smells 与重构手法

按用户问过的问题组织，每个问题对应一个坏味道及其重构手法。

### 需求模糊 → 怎么让 Agent 不猜？

一句话需求 → Agent 猜 → 猜错。重构手法是提取指令文件（AGENTS.md），三件套：

- **约束条件**：怎么做，写得越具体猜测空间越小
- **完成条件**：什么算做完了，必须可验证（「数据达标了」而非「感觉差不多了」）
- **边界情况**：异常怎么办，不写就不会处理

诊断信号按严重程度递增：Agent 反问 → 看起来对用起来不对 → 反复说「我不是这个意思」（伴随优先级丧失：对话中每句话权重相同，Agent 分不清核心约束和随口一说）。

### 虚假胜利 → 怎么防止 Agent 跳过难的宣布完成？

惰性生成：系统性回避需要更多推理的复杂部分，只处理容易的部分，然后自信宣布完成。三个特征：做快的、跳过难的但不告诉你、宣布完成。

终止条件失效的两个原因：**过度自信**（Agent 系统性高估自己的工作）和**认知统一**（生成和评估是同一个 Agent，盲点原样保留）。

消除手法：**分离执行与验证**。生成者只负责产出，验证者独立判断。验证者可以是脚本——判断逻辑写成代码就是可重复执行的验收测试。Agent 不再有权说「我做完了」。

### 指令腐化 → 为什么规则越加 Agent 越笨？

本质是「只增不减」：每条规则加进去时都有效，但累积后优先级冲突 + 矛盾 + 中间迷失叠加，行为失控。治理三件套：

- **优先级确定**：矛盾检测和清理都靠它裁决
- **矛盾检测**：显式矛盾可以处理，隐式矛盾让 Agent 随机选一条——矛盾本身不可怕，可怕的是一直隐藏着
- **定期清理**：规则登记表带过期条件字段，配置成定时任务或每次会话开始时检查

### 前馈痴迷 → 为什么写了规则还是出错？

根源：描述「怎么做」容易，描述「做完的结果」难。前馈 = 概率，反馈 = 证据。只有前馈没有反馈，Agent 会草率收工。

消除手法：**反馈优先**。加控制时先写结果检查形式，再写过程规则形式。检查不强制写成脚本：确定性的写成脚本，语义判断的留给 Agent。

### 上下文倾倒 → 信息给多了为什么反而差？

上下文预算：窗口和注意力都是有限资源，每段信息都要花钱。四种方法：

- **筛选**：决定给不给（最费人，放最后）
- **分层**：决定怎么组织（与双层循环天然配合）
- **按需加载**：决定什么时候给（索引和内容分离）
- **压缩**：决定以什么形式给（参考资料可以压，约束和验收标准不能压）

作者建议顺序：按需加载 → 压缩 → 分层 → 筛选。

### 上下文焦虑 → 接近窗口上限时为什么行为退化？

与惰性生成的区分：惰性生成随时可能发生，上下文焦虑只在资源压力下触发。治理手段：双层循环 + checkpoint + 上下文预算 + subagent。

### 跨会话知识丢失 → 新知识为什么没有渠道？

现有的两条同步通道（progress 和交付物）是按产物类型设计的，新知识不属于任何一类——归不了类就没有渠道。三类知识：用户统筹（优先级偏好）、发现（执行中发现的事实）、决策（模型或用户裁决）。操作：内层清点知识 → 外层归位（ADR/wiki/偏好文件）。

### 隐式约定 → 为什么 Agent 拿通用方案套项目上下文？

Agent 不了解不同模块实现方式的约定，拿通用方案套项目特有上下文。与模糊需求的区分：实现方式的澄清需要处理不同的优先级，不同模块因历史原因有不同的权衡。

消除手法：**建立原则文档（Establish Principles）**。不是规则清单，是决策框架——告诉你「当 X 和 Y 冲突时，优先选哪个」。文件结构三层：AGENTS.md 入口层、constitution.md 原则层、docs/decisions/ ADR 模块层。五个优先层级：红线 > 用户当面指令 > 项目级约定 > 模块级 ADR > 最佳实践。

### 信息散落 → 为什么文档比没有文档更糟糕？

知识纳入仓库后因更新不及时变成事实的旧版本。没有文档时 Agent 知道自己在猜；有文档但过时的时候，Agent 自信地执行错误的信息，而且这份自信来自你建立的仓库。

消除手法：**管理知识依赖**。仓库中每条信息都是一条知识依赖，依赖某个外部信息源。有 URL 或 API 的来源用 SOURCE.md + 定时 Skill 自动拉取；没有固定来源的在 AGENTS.md 加提醒环节让 Agent 主动询问用户。

### 反馈过载 → 为什么 Agent 来回横跳修不好？

反馈信号太多且没有分级，互相淹没。测试、lint、类型检查全失败，Agent 无法确定优先修复哪个，来回横跳。一个「数据引错了」的硬伤和一个「语气不够活泼」的风格偏好，在修改意见里看起来差不多。

消除手法：**分级反馈（Grade Feedback）**。核心思想是给反馈分级，Sensors 的数量并非要点。第一原则：成功静默，失败才输出。按严重程度分三级：阻塞级（不修无法工作）、警告级（应该修但不阻塞）、信息级（可忽略，默认静默）。分级的实质是责任分界：阻塞级是模型必须完成的，警告级由模型评估后人来决定，信息级通常可转化为前馈。三层足够，分更多级只是把反馈过载换成另一种形式。

### 状态污染 → 为什么状态存在但不可信？

本该随任务结束一起消亡的执行数据，混进了要跨会话复用的状态里。临时内容被当成长期事实，状态失去可信度。两个典型来源：工具给出误导的结果（「练习完成」其实 0 个词）；模型自己过度推断（一次用了虚拟式就认定「已掌握」）。

消除手法：**状态分区（State Separation）**。草稿纸（Scratchpad）：给执行数据单独划一个临时工作区，收尾时做整合（consolidation），把值得保留的内容提炼成带来源的知识条目。双层循环：内层短命会话隔离执行数据，外层管状态，审视者与执行者分离，Check 环节是天然的整合点。

关键判断：出现状态污染，往往说明任务复杂度已经超过当前 Harness 架构能处理的范围。

### 环境漂移 → 为什么 Agent 昨天能跑今天就不行了？

Agent 运行依赖的条件（运行时、依赖、外部服务、模型）没有被显式声明和锁定，却在悄悄变化。时间上的漂移：API、模型随时间改版，同一台机器上行为悄悄变了。空间上的漂移：换台机器就失效。

消除手法：**环境锁定（Lock Environment for Agent Harness）**。用软件工程里成熟的 lockfile 范式。init.sh 固定运行环境；lockfile 锁定运行时与依赖；第三方 Skill 局部化到项目内部、pin 住版本；外部服务交给 MCP 间接层吸收；完成局部化后打包成 Docker image 分发。

### 模式复制漂移 → 为什么 Agent 总在抄你最想淘汰的代码？

仓库里既有的产物本身就是 Agent 的学习材料，它会把自己读到的模式复制下去。三个成因：训练目标奖励「接得像」；指令与范例冲突时范例权重更高；检索排序把旧代码排前面。

消除手法：**模式基线化（Pattern Baseline）**，分四步：正向范例（给出新写法的样子，放在仓库固定位置）；确立架构约束（把约定变成会失败的自动化检查，强制不变量不微观管理实现）；建立基线（现存违规冻结，只许减少不许增加）；持续清理（改到哪清到哪）。前两步的分工：范例给方向，约束给边界。


## Skills 最佳实践 → 怎么写出可预测的技能？

技能好坏的判断标准是**可预测（Predictability）**：每次跑出类似的过程，不是相同的输出。结果每次可以不一样，但先做什么、后做什么、什么算做完必须稳定。

四个实践全部落在内层循环（Guides → Action → Sensors → Steering）结构上：

### 明确触发

description 是唯一常驻上下文的字段，也是唯一参与竞争的位。要在几十上百个技能里被选中，重点写「什么时候用」，而不是「这个技能能干什么」。两个技能描述撞车时，把「不该用在哪儿」也写进去。有 description 的技能是模型调用（Model-Invoked），摘掉 description 后变成用户调用（User-Invoked）——前者有模糊性但灵活，后者消除模糊性但认知负载全压在人身上。

### 恰当的自由度

自由度量的其实是内层循环四环节里有多少交给模型：

- 低自由度：四环节全定死，模型只执行 Action
- 中自由度：Guides 和 Sensors 定住，Action 里的选择交给模型
- 高自由度：只给 Guides 的方向和 Sensors 的标准，Action 和 Steering 都交给模型

不同任务对确定性的要求不同，选哪一档看这一步做错了能不能倒回来。

### 体积控制与划分

先看结构再看数字。先查四环节缺不缺（缺失比臃肿更常见），再看哪一环膨胀：前馈膨胀对应前馈痴迷，反馈膨胀对应反馈过载，Action 膨胀是自由度问题（该给方向的地方定住了），Steering 膨胀是异常决策树太大（只留关键转向）。结构没问题之后才看行数与 token——实测拐点是 500 行 / 5000 token。

分开判据：能否提取独立触发器，且分出来的技能必须有完整的四个环节。只有 Action 的不算新技能，只是被挪走的一段说明；只有 Sensors 的说明它应该是分级反馈里的一步。

### 内层循环本身即是最佳实践

四个实践不是独立的技巧清单，都叠加在内层循环结构上。配合前面的坏味道重构（保证流程一致性）和知识固化，写技能就不是难事。

## 人的介入 → 自动化之后，人还在哪一点进入？（第 22 讲）

双层循环负责「做对」，人负责判定「什么是对的」：方向和标准不能交给机器。介入有五种方式：完全介入、动作前批准、提交前批准、异常升级、完全自主。按任务选择，目标是「更少、更高价值的介入」。

四个衡量维度是政策、价值、外部性、可逆性；评估时先看政策/价值/外部性，最后看可逆性，并算累计风险总账。可逆性不是免死金牌：泄露的密钥和发出的消息收不回来。审批过频会发生**橡皮图章**——原文引用的经验数字是每小时超过二十个审批请求后，人开始在超过九成五的请求上不看就批。

动作前批准必须落在**工具网关**（统一 dispatch 上的 allow / ask / deny），不能只写「高危操作先问我」的提示词。异常升级依赖**校准后的置信度阈值**：先拿有标准答案的样本集校准，再设临界值。

## 自我改进 → 技能多了以后，靠什么决定留、改、扔？（第 23 讲）

四件事：**生命周期管理、验证、抽象、维护**。验证是核心，实现方式是给技能配 Eval。

三类信号：触发精度（漏触发/误触发）、输出质量（结果/步骤/风格）、效率（延迟/token/成本，必须与质量成对看）。评估四步：写 10–20 条用例并加「不该触发」负面控制 → 隔离运行 → 确定性检查 + rubric 两层打分 → 对比。对比有两个基线：上一版分数，以及**卸掉该技能的裸模型分数**——后者测「净提升」；若裸模型也全过，技能应考虑退役。

## Loop Engineering → 外层 PDCA 怎么写成会自己跑的系统？（第 24 讲）

外层 PDCA 本质就是一个 Loop。改写成循环工程时：Plan 写成 **goal + done signal**；Do 触发内层循环；Check 换成客观 **verifier**，并在状态里记录轮次防空转；Act 写成 stop / retry / escalate 规则。

`state/loop.md` 每轮追加「做了什么 / 检查结果 / 下一步」。停止条件：完成、达到轮次上限、连续 N 轮无进展、范围外动作、权限/认证/安全错误。`/goal` 进一步简化时，人只写 Check（完成条件 + 轮次上限），Plan/Action 交还 Agent，Do 交给技能；这只适合完成条件简单的任务。

## 多 Agent 编排 → 什么时候该拆，什么时候不该拆？（第 25 讲）

每多一个 Agent，就多一处失败点、多一套提示词、多一次交接损耗；token 消耗通常是单 Agent 的 **3 到 10 倍**。只值得用于**严格工作流、多路并发、上下文隔离**三类场景；为「看起来高级」而拆是交嫉妒税。

TradingAgents 四层（分析师并行 → 多空研究员辩论 → 交易员 → 风控与基金经理审批）里，绝大多数交接是结构化报告，只有多空辩论等需要对立观点碰撞的地方用自然语言——**该结构化就结构化，该对话才对话**。

轻量替代：固定工作流用**状态文件 + `/loop`**（消息换状态文件，先后换文件依赖，代价是轮询触发不如自主编排及时）；只要并发或上下文隔离，用 **Subagent**（如 `context: fork`），无需多 Agent 协调器。

## 内部 Harness → 什么时候才该动自我纠正循环本身？（第 26 讲）

第一原则：**不要构造内部 Harness**。内部自我纠正循环高度趋同，业务差异在外部四个子系统。只有循环行为、上下文取舍、工具执行策略与任务明显冲突时才改。

DeepSeek Harness 的五环节可插拔：agent loop、工具流水线、会话日志（「模型可见即已记录」）、系统提示词组装、模型适配。改 agent loop 靠三个扩展点：**pre-step**（入口放行/拒绝/改写）、**request**（请求前换模型与提示词）、**turn-stopping**（收尾前强制再检查）；还可在任务完成后加自动提取 Skill 的新步骤。

高频稳定的外层规则可从提示词固化进 agent loop（如「连续三轮无进展就停」写进 turn-stopping），换来准确和高效；内置循环已能做好就不要固化。

## Agent First Workspace → 外部 Harness 的基准形态是什么？（第 27 讲）

人打断 Agent，几乎总因为缺「做什么 / 怎么做 / 当前状态 / 什么时候停」。第一原则是**前置**：把运行时由人回答的东西提前写成工作区工件，让 Agent 去读而不是去问。人从「执行中的应答者」变成「开始前的规格作者」。

知识库装的是「让知识可获得的机制」，有四个来源：**人写的地图/约定/意图**（写到哪去读，复述会腐烂）、**系统已有的代码/配置/git 历史**（指向活源头）、**Agent 派生的探索/索引/结构/摘要**（自动生长）、**Agent 沉淀的决策/踩坑/纠正**（写回去，每个问题只解决一次；经人认可可升级为新的锚定范例）。

下发任务是两段式：先下**设计令**（人给说明 → Agent 出方案与 todo → 人审方向、增减检查点），再下**执行令**（进 loop）。审设计是人的判断成本最低、价值最高的位置。

## 写课 Workspace 实例 → 知识库在生产中怎么用？（第 28 讲）

目录分三责：知识库（前一门课原稿做风格锚定 + 行业摘要索引）、产出物（`outlines/` 与 `lessons/` 分开，防提纲污染正文）、Harness（`AGENTS.md` + `skills/`）。

知识库的两个用途是**交叉验证**（核对课程方案是否仍最优，例如作者因与已有坏味道重合而舍弃 `progress-mirage`）和**替换保密实例**（客户案例换成公开案例）。九步流程前四步属外层、五到八步属内层、第九步收尾；可自主的是抓更新、复审旧稿、建议主题、找正反例、查重，核心立意与审稿判断留给人。

## 遗留系统（一）→ 业务信息补不全时，知识库锚在哪？（第 29 讲）

「先补全业务再开工」在遗留系统上几乎走不通；唯一完整留存的事实源是**代码**。AI 读代码能懂「系统在做什么」，对「系统是什么」只能推测；代码里看不懂的绕弯与补丁正是丢失业务信息的影子，业务背景只作补充。

**按架构压缩**：架构是筛掉实现细节后的高密度骨架，**骨架常驻索引，细节按需回源码读**。索引要从 Agent 视角画在**微服务边界**上（服务职责、调用关系、数据所有权），因为单个服务内部 Agent 随时能重读，跨服务关系才是它拼不出来的。

三 Skill 递进：`repo-index`（仓库地图，README 只当线索）→ `api-contracts`（每服务 `api.spec.md` + `api.contract.md`，不明标「待确认」）→ `service-map`（contract 与 spec 对照反查提供方，拼 mermaid 依赖图，对不上画虚线）。

## 遗留系统（二）→ 知识库怎么被任务和测试持续校准？（第 30 讲）

知识提取是**任务驱动**的：spec/contract 只是接口知识，回归测试还要行为知识；任务没来就不知道缺哪块，遇缺即补。

`implement-flow` 从每个 endpoint 画出 mermaid 调用链（下游 API、数据库、消息、分支），它既是几乎无损的上下文压缩，也是现成的测试提纲。`test-case-design` 逐项提取案例，**「待确认」节点列为最高优先级的探针测试（固化现状）**；`test-implement` 只加测试不改生产代码，mock 照抄仓库现有模式。

**探针测试跑挂了是信息，不是 bug**：说明现状与推测不符，把实测真实行为**回写 `endpoint-flows.md`**，知识库被测试反向校准。最后把 `AGENTS.md` 从目录说明升级为能力清单：每类任务怎么触发、走哪条 Skill 链、产出什么文件。

## 结束语 → 判断力的位置

课程反对把全课当成现成代码库或万用 Skill：重构与 Harness 的重点都是过程与判断力。四环节的人机分工是 **Guides 归人、Steering 归人、Action 归 Agent、Sensors 尽量归机器**。十三个坏味道的价值是提供可迁移的 Debug 诊断力——把「Agent 让我失望」退回具体环节。原文判词：**「把判断外包出去，不是驾驭，是缴械。」**（结束语原文没有「三层闭环」这一术语。）

## 全课概念分层与关系网络

把 33 篇正文的概念抽离讲次后，可归纳为五层：

1. **元哲学与人机主权**：Agent = LLM + Harness；人握 Guides 与 Steering，Agent 跑 Action，机器守 Sensors。
2. **四个原子骨干与四大子系统**：前馈（Guides）、行动载体（Tools & Skills）、反馈（Sensors）、状态与环境。
3. **双尺度运行骨架与两条物理法则**：内层 Steering Loop（Guides → Action → Sensors → Steer）与外层 PDCA/Loop；计算型与推断型分离；自由度三档，以及启发式重规划与照图走的权衡。
4. **四大子系统的腐化与修复配对**：前馈病（07/08/09/11）、反馈病（10/12/13）、状态与上下文病（14/15/16/17）、环境与模式病（18/19）。
5. **规模化模式、工作区合成与自我演进**：Skills 写法与四角度锚定、介入刻度、多 Agent 边界、内部 Harness 三扩展点、Agent First Workspace、遗留系统实战，以及 Eval 驱动的 Skill 生命周期。

贯穿这些层的六类关系：

- **合成**：四骨干在单任务尺度合成内层循环，在跨任务尺度合成外层 PDCA。
- **镜像互补**：前馈与反馈缺一不可；前馈痴迷（缺反馈）与反馈过载（反馈无序）互为镜像。
- **递进**：同一「上下文有限」问题，依次由预算四法（14）→ Checkpoint（15）→ 前置为工作区工件（27）→ 按架构与调用链压缩（29/30）回答。
- **连续谱权衡**：启发式 PDCA ↔ `/goal` 半固定 ↔ 流程锚定/状态文件 + loop ↔ 外层规则固化进代码。
- **示范压倒指令**：旧代码示范会压过新指令，所以要有正向范例 + 自动化约束 + 存量基线 + 持续清理（19），再延伸为四角度锚定（21）。
- **反向校准飞轮**：第 23 讲是 Eval 决定 Skill 留/改/退役；第 30 讲是探针测试把实测行为回写知识库。

## retro 与动态知识更新的关系

retro skill 不对应课程的动态知识更新。retro 是对一次会话做回顾，找出**环境改进点**（导航指针、自动化检查、编码标准、工具经济性），按严重程度向用户展示候选项。它改的是 Harness 的基础设施，与知识归位到 ADR/wiki/偏好文件无关。

auto-extract 更接近课程的动态知识更新：从对话提取三类内容（用户纠正、隐含偏好、经验），四层分类（用户/项目/子模块/情境），归位到正确的存储位置。

## Overview

徐昊课程的核心框架：Agent 驾驭通过两层循环实现——外层 PDCA 管任务分解与进度追踪，内层操控循环（Steering Loop）管具体执行中的质量控制。操控循环由前馈（Guides）、行动（Action）、反馈（Sensors）、调整（Steer）四个环节组成。这个框架与 Birgitta Böckeler 在 Fowler 网站上提出的 harness engineering（guides/sensors/steering loop）高度对应，但术语来源不同：徐昊借自控制论（control theory），Böckeler 用工程语言。

## 自我纠正循环是 ReAct 的特殊形式

自我纠正循环没有额外机器。OMP 的 `#runLoop` 里没有任何叫「纠正」的部件——工具失败被包成 `isError: true` 的 toolResult 追加进历史，下一次请求带着它，模型自己决定换做法。全过程就是循环的「观察」环节碰巧观察到了错误。

观察分两类：

1. **显式失败**：工具返回错误（TypeError、exit code 非 0）。模型想不看见都难。
2. **隐性质量缺口**：工具成功了但结果不对。没有 `isError` 标记，模型必须自己从成功输出的内容里读出「这不行」。

第 2 类才是自我纠正的难点。要触发第 2 类，需要有人把质量缺口变成可观察的信号——这就是反馈控制（Sensors）的作用。没有传感器制造观察，循环转得再好也看不到该纠正什么。

## Steering 是操控循环的第四步

操控循环四步：

1. **Guides**（前馈）：告诉 Agent 要做什么、怎么做
2. **Action**（行动）：Agent 执行任务
3. **Sensors**（反馈）：检查结果是否符合标准
4. **Steering**（调整）：根据反馈决定下一步——继续、重做、修正、还是求助

如果 Agent 做完一步就等人来指出错误，那它自己就没有在执行第四步——调整的工作被人包办了，Steering 这个设计环节就空转了。

## Edge 是窗口截断边界

课程原文（第 5 讲）说「多余的信息会把真正重要的指令挤到窗口边缘，随着对话进行被截断或压缩」。edge 是**上下文窗口的截断边界**——内容掉出窗口，信息丢失。具体到 OMP 的实现（源码核验）：system prompt / 指令是 pinned 的，不会被驱逐；溢出时丢弃或压缩的是最早的非固定对话轮次，最近的尾部和固定的头部都保留。

这与「注意力漂移」是两个独立机制：

- **上下文溢出**：窗口物理上限，内容被截断/压缩，信息丢失
- **注意力漂移**：窗口够大、内容还在，但注意力被无关信息稀释，响应质量下降

## Guides vs Sensors 的融合边界

Böckeler 的做法是把修正指引**写进 sensor 的输出**——lint 报错消息本身包含「优先重构，提高阈值是绝对例外」。这不是写在 AGENTS.md 里的独立 Guide，而是通过 sensor 这个反馈通道传递的前馈内容。

所以「这是 feedforward 还是 sensor？」的准确答案是：**内容上是 feedforward（告诉 Agent 该怎么做），传递方式上是通过 sensor（反馈通道）**。Böckeler 的核心创新就是这个融合——把修正指引嵌入反馈信号里，让 Agent 在看到错误的同时也看到怎么改。

## Feedforward 术语起源

Feedforward 这个术语是 I. A. Richards 在 1951 年第八届 Macy 控制论会议（Macy Conference on Cybernetics）上创造的，明确作为 feedback 的对应词。OED 记录了这个起源。起源在 cybernetics 内部，后传入 control theory。

Cybernetics（控制论）是 Wiener 1948 年创立的跨学科领域，研究一切系统的控制与通信。Control theory（控制理论）是工程学分支，专门研究动态系统的数学建模与控制器设计。前馈/反馈的明确区分来自 control theory，但术语本身起源于 cybernetics。


## 概念对应关系

| 徐昊（控制论术语） | Böckeler（工程术语） | 含义 |
|---|---|---|
| 前馈（Feedforward） | Guides | 执行前告诉 Agent 该做什么、怎么做 |
| 反馈（Feedback） | Sensors | 执行后检查结果是否符合标准 |
| 调整（Steer） | Steering loop | 根据反馈决定下一步 |
| 自我纠正循环 | Self-correction loop | ReAct 的特殊形式，观察改为自我纠正 |
