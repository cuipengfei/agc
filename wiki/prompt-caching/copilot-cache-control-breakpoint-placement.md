## Overview

在多轮会话的大语言模型网关与开发工具中，`copilot_cache_control: { "type": "ephemeral" }` 按消息挂载，用于给显式断点缓存模型标记可复用前缀的切分点。多个客户端都尝试在发往各类后端（包括 Gemini）的请求中注入这个字段，但各项目的断点选点策略存在显著差异。同时，受控对照表明该字段对采用隐式前缀匹配的模型没有产生确定性的命中收益。本篇梳理不同代理客户端的选点算法模型、隐式与显式缓存对断点标记的反应差异，以及在多层网关架构下保持缓存标记幂等与策略隔离的工程机制。

## 各客户端的选点策略

各网关与插件实现根据各自对会话结构的假设，发展出几种不同的标记放置算法：

| 选点模式 | 代表实现 | 算法特征 | 假设依据 |
|---|---|---|---|
| **双端启发式** | caozhiyuan/copilot-api | 固定选取前 2 条非空 `system` 与最后 2 条非空非 `system` | 假设最稳固的是系统提示词，最频繁复用的是最近一轮对话上下文 |
| **差异化路由** | 本机 copilot-api | 对支持四标记的模型实施逆扫贪心算法；其余请求沿用前 2 条 `system` 加尾部 1 条 | 按模型真实能力分流，避免在通用调用链上产生未预期的标记冲突 |
| **四标记逆向贪心** | VS Code Copilot 官方实现 | 逆向遍历：优先标记当前用户输入、当前轮次工具批次末尾、以及纯回复形态的 assistant 消息；配额未耗尽时由前向后填充系统与早期指令 | 动态优先保护最近轮次的复杂调用链，在长上下文下保持高价值断点 |
| **Token 权重排序** | CodeCompanion.nvim | 按估算 token 长度对消息降序排序，取长度最大的前 4 条非空消息挂载 | 假设长消息（如系统长指令、大文件注入）具有最大的缓存节约价值 |
| **透明透传** | ghcp_proxy | 仅保留上游或客户端已有标记，网关自身不实施主动选点 | 将断点决策权完全交给最贴近上下文构建的应用层 |

## 显式断点与隐式前缀匹配的机制差异

大模型服务商的上下文缓存实现通常分为显式（explicit breakpoint）与隐式（implicit prefix matching）两种机制：

1. **显式断点缓存**：模型后端明确要求客户端指定哪些消息节点作为持久化快照锚点（例如 Anthropic 协议与 Copilot 协议的 `ephemeral` 标记）。若没有标记，后端可能不建立跨请求快照。
2. **隐式前缀匹配**：模型后端（如 Google Gemini / `gemini-4-argon`）由服务端自动根据输入字节或 token 序列的最长公共前缀匹配已有缓存，客户端无需也不读取任何断点元数据。

在隐式前缀机制下，同账户的成对对照没有出现稳定方向的差异。在公开社区的追踪记录中，请求完全不带标记时，重发相同内容输入 219,575 tokens 依然能命中 217,526 tokens；同时同一报告的长期平均命中率仅有 27%。这证实了采用隐式缓存的后端在没有标记时也能达成高命中，而命中波动主要受服务端驱逐策略与负载影响，并非缺少断点标记所致。

因此，对只支持隐式缓存的模型而言，注入 `copilot_cache_control` 本质上是保持协议兼容与字段无害透传，无法替代良好的会话前缀管理。

## 真正影响缓存命中的架构因素

对隐式缓存与显式断点缓存而言，决定缓存命中与否的核心约束都是**最长公共前缀的连续性**。任何对前缀中途的修改都会使后续所有内容失效：

- **会话中段的就地改写**：如历史消息压缩、工具输出裁剪（例如 Shake 机制）；
- **动态变量注入**：在系统提示词或前几轮指令中动态注入每轮变化的当前时间戳、随机数或临时状态；
- **重试流的非确定性结构**：因网络重试而改变了中间某条消息的 role 序列。

保持高命中率的收益主要来自于应用层对前缀稳定性的维护，而非在尾部尝试多打断点。

## 多层网关下的选点实现边界

在实现多标记逆向贪心算法时，存在两个直接影响算法正确性的实现细节：

1. **重放状态下的边界判定顺序**：在逆向扫描中，算法需要识别哪些消息属于“当前用户轮次之后”。若实现中将“跳过已有标记”的逻辑置于“更新用户边界标志”之前，当最新用户消息本身已被挂载标记时，该状态位将无法正常反转，导致该消息更早的历史记录被错误判定为当前轮次。稳健的实现必须将轮次边界状态更新与单条消息已有标记的检查彻底解耦。
2. **循环前置配额守卫**：算法在进入逆向遍历前，应先统计现有消息已占用的标记总量。若上游客户端已完整注入足额标记（如达到 4 个），应直接退出遍历并返回，避免在内部循环条件不严谨时溢出配额追加第 5 个标记。
3. **分层路由与策略单向性**：在具备协议转换的多层网关中（例如将 Messages 接口映射至 Chat 接口，或在多模型间做 fallback 重试），标记注入策略必须在第一次入口转换时根据最终目标模型的真实 metadata 确定，禁止在第一层先应用通用规则、再在第二层追加特定规则，否则容易造成标记碎片化与配额提前耗尽。
